# 資料架構與 Schema

## 為什麼要改

原本的資料就是 API 回應原封不動存檔，一個「學年度-學期-學制-學院」一個檔，1084 個檔、112 MB。三個問題：

1. **一門課被存了很多次。** raw 的一列不是一門課，是一個「開課班級」。同一門課開給 6 個班級就有 6 列，內容只有 `cls_id` / `cls_name` 不同。全部 145,632 列實際上只有 120,643 門課，17% 是重複。
2. **上課時間是無法使用的字串。** `scr_period` 長這樣：`(二)06-07 資電B06 (五)09     資電107 劉維正` — 週次、節次、教室、教師全擠在一起。任何前端都得自己寫剖析器。
3. **以學院分檔是錯的維度。** 約 1% 的課同時掛在多個學院底下（例：`1001` 的選課代號 `4213` 同時出現在 CB、CF、XH），0.8% 跨學制。學院是**關係**不是屬性，拿它當目錄結構就必然造成跨檔重複。

## 主鍵

`(學年度, 學期, 選課代號 scr_selcode)`。

在全部 145,632 列、100–115 共 16 個學年度的資料上驗證過：**零衝突**（同一組鍵對到的 `sub_id` 永遠唯一）。

## 目錄結構

```
100/ … 115/          原始 API 回應，保持不動（既有深連結不會壞）
data/
  index.json         學期清單 + 學院／學制／節次時間對照
  {學年度}{學期}.json  一學期一檔，正規化後的課程陣列
scripts/build.py     raw → data 的 ETL（可重跑）
```

`data/` 由 `scripts/build.py` 產生並 commit 進 repo。歷史學期的輸出是 byte-identical，
所以每天重建實際上只有當學期的 1～2 個檔會進 git。

## 課程物件

```jsonc
{
  "id": "2144",              // 選課代號 scr_selcode，該學期唯一
  "code": "IEE2000",         // 科目代碼 sub_id3
  "subject_id": "02270",     // 科目流水號 sub_id
  "name": "工程數學(一)",
  "credit": 3,
  "required": true,          // 必修；選修時省略
  "degrees": [1],            // 學制，1 大學部 3 碩士 4 博士 5 進修
  "depts": ["CI"],           // 開課學院，可多個
  "unit": 4500,              // 開課單位代碼 unt_ls
  "teachers": ["劉維正"],
  "classes": [{ "id": "CI00101", "name": "資電學院綜合班" }],
  "sessions": [
    { "day": 2, "from": 6, "to": 7, "room": "資電B06" },
    { "day": 5, "from": 9, "to": 9, "room": "資電107" }
  ],
  "quota": 60,               // 限修人數
  "enrolled": 59,            // 已選人數
  "online": true,            // 線上教學；課堂教學時省略
  "english": true,           // 英語授課；否則省略
  "exams": [true, false, false], // 期中/期末/期初考，全 false 時省略
  "period": "2025/04/10 ~ 2025/06/17", // 非「全學期」時才有
  "section": "002",          // 分班，"001" 時省略
  "note": "限EMBA學生修習",
  "raw_period": "…"          // 僅在 sessions 剖析失敗時保留原字串（全庫 25 筆）
}
```

**所有 falsy 欄位一律省略**（`null` / `false` / `0` / 空陣列 / 空字串）。消費端一律
`course.english ?? false` 這樣讀。這讓未壓縮體積少了 22%，直接反映在瀏覽器的
`JSON.parse` 時間和記憶體上。

### 檔案排版：一行一門課

```json
[
{"id":"0001","code":"IND3453","name":"元宇宙入門-虛擬實境的藝術",…},
{"id":"0003","code":"IND3411","name":"Python程式編寫",…}
]
```

四種排版的實測（以 `1131.json` 為例）：

| 排版 | 未壓縮 | gzip | 一門課異動時的 `git diff` |
| --- | --- | --- | --- |
| 完全 minify | 1.27 MB | 135 KB | **2,550,448 bytes** |
| **一行一課（採用）** | 1.28 MB | 135 KB | **3,011 bytes** |
| `indent=2` | 2.15 MB | 148 KB | 約 3 KB |
| `indent=4` | 2.81 MB | 157 KB | 約 3 KB |

一行一課的 gzip 體積跟完全 minify **一模一樣**，未壓縮只多 0.8%，但因為 CI 每天
commit 一次，diff 從 2.5 MB 縮到 3 KB（847 倍）。`indent=2` 雖然更好讀，未壓縮卻要多
69%，那是瀏覽器每次都要付的 `JSON.parse` 成本，而想讀檔案時 `jq .` 隨時排得出來。

`data/index.json` 很小而且是給人看的，維持 `indent=2`。

### quota 與 enrolled

`quota` 是限修人數（`scr_precnt`），`enrolled` 是已選人數（`scr_acptcnt`）。

**`enrolled > quota` 很常見，佔 16.4%，那不是資料錯誤，是加簽。** 另有 2.5% 的課
`quota` 為 0（欄位省略後就完全不存在），通常是限修名額只作形式登記的課。

這兩個欄位的語意容易搞反，可以用分布驗證：`scr_precnt` 有 71.5% 是 10 的倍數、
只有 101 種相異值（60 就佔了 42%），是人工設定的上限；`scr_acptcnt` 只有 15.5%
是 10 的倍數且分布平滑（60 / 59 / 58 / 57 / 56 …），是實際人數。

### sessions

`day` 1–7 對應週一到週日。`from` / `to` 是節次，`0` 代表尚未排定。
`room` 為 `null` 表示「未排教室」或「待排」。

節次對應的實際時間放在 `index.json` 的 `periodTimes`，109 學年度起夜間節次有調整，
所以分成 `>=109` 和 `<109` 兩組。

剖析器覆蓋率 **99.982%**（145,632 筆中 26 筆失敗，去重後 25 筆），失敗的都是上游
資料本身缺了 `(週)` 前綴。

## 已知限制

- **沒有暑修（學期 3、4）資料。** 抓取程式只查上、下學期；官方 API 的暑修學院清單回空陣列。
- `unit`（開課單位代碼）目前只有數字沒有名稱對照。
- 教學大綱可從官方深連結取得，格式為
  `https://coursesearch02.fcu.edu.tw/CourseOutline.aspx?lang=cht&courseid={學年度}{學期}{選課代號}`，
  目前未納入本資料集。

## 體積

| | 檔數 | 未壓縮 | gzip |
|---|---|---|---|
| raw（原樣） | 1084 | 112 MB | — |
| data（正規化，一行一課） | 32 | 40 MB | 4.3 MB |
| 單一學期（如 `1131.json`） | 1 | 1.28 MB | 135 KB |

單一學期 138 KB 的 gzip 傳輸量，代表查詢網站可以一次把整學期載進瀏覽器做即時搜尋，
不需要任何後端。
